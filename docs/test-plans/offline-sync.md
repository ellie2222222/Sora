# Test plan: Offline sync (mobile, cross-cutting)

**Stories:** none of its own. This underpins every signed-in write story (TXN-US, ACC-US, CAT-US, BUD-US, SAV-US) while the device is offline.
**Design:** `plans/mobile/offline-sync-plan.md` (§3 local write model, §5 sync engine, §8 conflict handling, §11 verification plan); API spec §2.10 Idempotency
**Rules:** rule 17 (device-local data belongs to one account), MB-02 (RTK Query is the only server-state cache), BR-05 (optimistic figures are provisional and replaced by the server's)
**Code under test:** `mobile/src/services/sync/` (`offlineQueue`, `offlineQueueDb`, `sqliteQueueDb`, `syncEngine`, `entityAdapters`, `localCache`, `syncDatabaseOpen`, `pendingTotals`, `optimisticRecords`), `mobile/src/app/store/offlineQueueSlice.ts`, `mobile/src/app/store/api/signedInRead.ts`, `mobile/src/app/store/api/pendingTotalsPatch.ts`; and for an unreachable API: `utils/errors.ts` (`toApiError`, `isServerFault`), `services/auth/refreshRejection.ts`, `services/sync/{networkState,reachabilityProbe,sendOrQueue}.ts`, `hooks/connectivityNotices.ts`

## Objectives

1. A write made offline reaches the server exactly once, in order, under the account that made it.
2. A server refusal never silently drops a row: it is parked for the user.
3. Another account on the same device never sees, sends or claims these rows or the cached reads.
4. Optimistic figures match what the server will compute, and undo exactly on cancel.
5. An API that stops answering while the device keeps its internet (server down, a tunnel or gateway answering in its place) is treated as offline: no error screen, no sign-out, writes queued, and recovery noticed without a NetInfo change.

## Test data & environment

- `memoryQueueDb()` and `nextId()` from [sync/testSupport.ts](../../mobile/src/services/sync/testSupport.ts). `memoryQueueDb()` is the production `MemoryQueueDb` ([memoryQueueDb.ts](../../mobile/src/services/sync/memoryQueueDb.ts), the web build's queue), so the tests can't drift from it. `SqliteQueueDb` ([sqliteQueueDb.ts](../../mobile/src/services/sync/sqliteQueueDb.ts)) runs its real SQL against an in-memory Node `node:sqlite` database through a test-file adapter.
- `recordingAdapters` in `syncEngine.test.ts` stand in for the API and record each call.
- Queue ordering relies on `OfflineQueue.enqueue` making `createdAt` strictly increasing ([offlineQueue.ts:103](../../mobile/src/services/sync/offlineQueue.ts#L103)), not on wall-clock gaps.
